# Trajectory Collector Protocol — Version 1

Wire contract between editor clients (LazyVim reference client; future
Zed / VSCode / JetBrains clients) and the collector server.

Status: **version 1, frozen for implementation**. Any incompatible change
requires a protocol version bump (`"protocol_version": 2`) and a new
document; v1 endpoints keep serving unchanged payloads.

This document describes the implementation in
`server/src/{index,types,ingest,blobs,stats}.ts` and
`nvim/lua/tabcomplete_trajectory/*.lua`. Where an older draft of this
document disagreed with the code, the code won and the document was fixed.

Design rule: the collector stores **raw, replayable trajectories only**.
It never constructs training examples, RL pairs, or labels. Pairing of
pre-edit state, proposals, feedback, and aftermath happens offline at
dataset-build time (see §11).

## 0. Conventions

- Transport: HTTP/1.1 + JSON (`Content-Type: application/json`) on every
  endpoint, including blob upload (base64 inside JSON, see §7). The server
  does not implement `Content-Encoding` negotiation.
- `protocol_version`: integer `1`, returned by `GET /healthz` and
  `GET /v1/stats`, and required in every POST body that carries it.
- Event timestamps: **integer milliseconds since the Unix epoch (UTC)** in
  every `timestamp_ms` field. Clients use wall-clock time; ordering is
  defined by `sequence_number`, never by timestamp.
- Session timestamps (`started_at`, `ended_at`) are **ISO-8601 strings**
  (e.g. `"2026-09-20T00:00:00.000Z"`). `POST /v1/session/end` tolerates a
  missing `ended_at` and substitutes server time.
- IDs: `machine_id`, `session_id`, `event_id`, `repo_id` are **opaque
  non-empty strings**. Clients SHOULD generate UUID v4
  (`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`, lowercase):
  - `machine_id`: generated once per client machine, persisted in the
    machine-id file (see README). Stable across sessions.
  - `session_id`: generated by the client at session start, echoed back by
    `POST /v1/session/start`.
  - `event_id`: generated by the client per event, used for dedup.
  - `repo_id`: client-chosen repository key (reference client uses
    `"repo:<root_name>"`); file rows hang off it.
- Rows/columns: **ZERO-based**. First line of a file is row 0, first column
  of a line is column 0. Ranges are end-exclusive.
- Request body cap: **10 MiB** on every endpoint. Larger bodies are rejected
  with `413` (see §3). Batch and compress accordingly.

| Method | Path                      | Purpose                              | Success |

### 1.1 `GET /healthz`

No request body.

Response `200`:

```json
{
  "status": "ok",
  "protocol_version": 1
}
```

### 1.2 `GET /v1/stats`

No request body. Every metric below is always present.

Response `200`:

```json
{
  "protocol_version": 1,
  "db_path": "/data/collector.sqlite",
  "db_bytes": 134217728,
  "wal_bytes": 4096,
  "blob_count": 310,
  "blob_original_bytes": 48200120,
  "blob_stored_bytes": 12000110,
  "compression_ratio": 0.249,
  "event_count": 48120,
  "session_count": 12,
  "repository_count": 11,
  "file_count": 88,
  "file_version_count": 310
}
```

Metric definitions:

| Metric | Meaning |
|--------|---------|
| `protocol_version` | protocol served (always `1` here) |
| `db_path` | SQLite path the server has open |
| `db_bytes` | current SQLite main-file size in bytes |
| `wal_bytes` | current SQLite WAL-file size in bytes (0 when checkpointed) |
| `blob_count` | unique blobs in store |
| `blob_original_bytes` | sum of stored blob bytes pre-compression |
| `blob_stored_bytes` | sum of stored blob bytes post-compression |
| `compression_ratio` | `stored / original`, or `null` when no blobs |
| `event_count` | unique events stored |
| `session_count` | sessions rows |
| `repository_count` | repository rows |
| `file_count` | file rows |
| `file_version_count` | file-version rows |

### 1.3 `POST /v1/session/start`

Request:

```json
{
  "protocol_version": 1,
  "session_id": "3f9d2c1a-1111-4b22-8ccc-0123456789ab",
  "machine_id": "7a4e8f2c-2222-4d33-9ddd-0123456789ab",
  "repo_id": "repo:foo",
  "started_at": "2026-09-20T00:00:00.000Z",
  "cwd_name": "foo",
  "git_head_at_start": "9f3a1b2c",
  "git_branch_at_start": "main",
  "editor": "nvim",
  "editor_version": "0.12.0",
  "plugin_version": "0.1.0",
  "platform": "linux",
  "hostname_hash": "abc123",
  "root_name": "foo",
  "root_identity_hash": null,
  "origin_url": "https://github.com/example/foo.git"
}
```

| Field | Required | Notes |
|-------|----------|-------|
| `protocol_version` | yes | must be `1` |
| `session_id` | yes | client-generated opaque id |
| `machine_id` | yes | stable client machine id (upserts `machines`) |
| `repo_id` | no | repository key; when present a repo stub row is inserted so the session FK is satisfied before the first snapshot |
| `started_at` | yes | ISO-8601 string |
| `cwd_name` | no | basename of the client working directory |
| `git_head_at_start` / `git_branch_at_start` | no | VCS revision / branch if available |
| `editor` / `editor_version` / `plugin_version` | no | free-form version strings |
| `platform` / `hostname_hash` | no | machine-level extras, upserted into `machines` |
| `root_name` / `root_identity_hash` / `origin_url` | no | repo stub fields; `origin_url` is sanitized (credentials stripped, never stored) |

Response `201`: `{ "session_id": "<same>", "deduped": false }`.
Sending a `session_id` that already exists returns `200` with
`{ "session_id": "<same>", "deduped": true }` (idempotent; original row
untouched). Unknown JSON fields are ignored.

### 1.4 `POST /v1/session/end`

Request:

```json
{
  "protocol_version": 1,
  "session_id": "3f9d2c1a-1111-4b22-8ccc-0123456789ab",
  "ended_at": "2026-09-20T01:00:00.000Z"
}
```

`ended_at` is optional; when absent the server substitutes its own time.
Response `200`: `{ "session_id": "<same>", "ended_at": "<iso>" }`.
Ending an unknown session returns `404`. Ending twice returns `200`
(idempotent; second call overwrites `ended_at`).

### 1.5 `POST /v1/events/batch`

Request:

```json
{
  "protocol_version": 1,
  "events": [ { "<envelope, see §4>" }, "..." ]
}
```

Rules:

- `protocol_version` MUST be `1`.
- `events` MUST be a JSON array; an empty array returns zeroes and stores
  nothing.
- Recommended batch: ≤ 500 events or ≤ 1 MiB (see §9 batching guidance);
  hard cap is the 10 MiB body limit (`413` past it).
- Per-event validation failure rejects the whole batch with `400` and stores
  nothing from that batch (atomic batches).
- Dedup is by `event_id` (primary key) and by
  `(session_id, sequence_number)` (unique): re-posts are skipped silently
  and counted in `skipped_duplicate` (`INSERT OR IGNORE`; no `409` in v1 —
  a conflicting sequence with a different `event_id` is dropped as a
  duplicate, not an error).
- Posting events for an unknown session returns `404`. Unknown JSON fields
  on the batch or on envelopes are ignored.

Response `200`:

```json
{
  "ingested": 499,
  "skipped_duplicate": 1,
  "total": 500
}
```

### 1.6 `POST /v1/blobs/check` (check-before-upload)

Clients MUST check before uploading: buffer contents are addressed by
sha256, and unchanged files share hashes.

Request:

```json
{ "hashes": ["e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855", "..."] }
```

Each entry must be a 64-char hex sha256 (case-insensitive).

Response `200`:

```json
{ "missing": ["<sha256 hex, only the ones the server lacks>"] }
```

The client uploads only the hashes listed in `missing`.

### 1.7 `POST /v1/blobs/upload`

JSON body (`Content-Type: application/json`):

```json
{
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "content_base64": "<base64 of the raw bytes>",
  "mime_type": "text/plain",
  "already_compressed": false
}
```

- `sha256` (required): server hashes the decoded body and rejects mismatches
  with `400`. Stored lowercase.
- `content_base64` (required): non-empty base64 of the **raw** bytes.
- `mime_type` (optional): hint for storage compression.
- `already_compressed` (optional boolean): when `true`, bytes are stored raw.
- Storage compression: text-like bytes are gzipped at rest
  (`compression: "gzip"`); bytes that look already compressed (gzip / png /
  jpeg / zip / bzip2 / xz / zstd / gif / webp / pdf / ico magic, a
  compressed `mime_type`, or `already_compressed: true`) are stored raw.
- Response `200` (both first store and re-upload):
  `{ "sha256": "<same>", "original_bytes": 12345, "stored_bytes": 3210, "compression": "gzip", "deduped": false }`.
  Re-uploading an existing hash returns the same shape with
  `"deduped": true` (single row; counted once in `blob_count`).

### 1.8 `POST /v1/repository/snapshot`

Manifest of the repo state. File contents travel as blobs (§7); this
endpoint carries only the manifest. The server sanitizes `origin_url`
(credentials stripped) and upserts the repository row plus one file row per
`relative_path` and one version row per `(file, sha256)` (re-snapshots of
identical content insert zero new versions).

Request:

```json
{
  "protocol_version": 1,
  "repo_id": "repo:foo",
  "root_name": "foo",
  "root_identity_hash": null,
  "origin_url": "https://github.com/example/foo.git",
  "observed_at": "2026-09-20T00:00:00.000Z",
  "default_source": "repo_scan",
  "files": [
    {
      "relative_path": "src/main.ts",
      "extension": ".ts",
      "language": "typescript",
      "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "observed_at": "2026-09-20T00:00:00.000Z",
      "source": "repo_scan"
    }
  ]
}
```

- `relative_path` is repo-relative with `/` separators, never leading `/`.
- `sha256` is required per file entry (64-char hex).
- `source` is one of `repo_scan`, `buffer_open`, `buffer_write`,
  `session_anchor`, `periodic_anchor` (per-entry, else `default_source`,
  else `repo_scan`).
- Version rows may reference blob hashes not yet uploaded: the
  `file_versions → blobs` link is intentionally a logical (non-FK) reference
  so manifests can be ingested before the corresponding blob bytes arrive.

Response `200`:

```json
{
  "repo_id": "repo:foo",
  "files_upserted": 2,
  "versions_inserted": 2,
  "versions_skipped_duplicate": 0
}
```

## 2. Status codes

| Code | Meaning | Used when |
|------|---------|-----------|
| 200 | OK | health, stats, session-end, batch, check, upload, snapshot, idempotent repeats |
| 201 | Created | session start (new) |
| 400 | Bad request | malformed JSON, schema violation, unknown event type, sha256 mismatch |
| 404 | Not found | unknown `session_id`, unknown endpoint |
| 405 | Method not allowed | non-POST on a POST route |
| 413 | Body too large | request exceeds 10 MiB |
| 500 | Internal error | server-side failure; client SHOULD retry with backoff |

## 3. Error objects

Every non-2xx response returns flat JSON:

```json
{
  "error": "bad_request",
  "message": "events[3]: event_type must be one of: ..."
}
```

Observed `error` strings: `bad_request`, `not_found`,
`method_not_allowed`, `payload_too_large`, `internal`.
Clients branch on `error`, never on `message` text.

## 4. Event envelope

Every element of `events[]` carries its type in **`event_type`**
(not `type`) with type-specific data in `payload`:

```json
{
  "protocol_version": 1,
  "event_id": "9c1d3a55-4444-4e55-8fff-0123456789ab",
  "session_id": "3f9d2c1a-1111-4b22-8ccc-0123456789ab",
  "sequence_number": 4812,
  "timestamp_ms": 1758360000789,
  "event_type": "edit_delta",
  "file_id": 7,
  "changedtick": 12,
  "cursor": { "row": 11, "col": 11 },
  "mode": "n",
  "payload": { "...type-specific, see §5..." }
}
```

| Field | Type | Rules |
|-------|------|-------|
| `protocol_version` | int | optional per event; when present must be `1` |
| `event_id` | non-empty string | client-generated, globally unique (UUID v4 recommended) |
| `session_id` | non-empty string | must equal a started session |
| `sequence_number` | non-negative int | ordering key within the session; duplicates deduped (§1.5) |
| `timestamp_ms` | non-negative int ms | client wall clock; informational only |
| `event_type` | string | one of the 19 types in §5 |
| `file_id` | int or null | server-assigned `files.file_id` when known, else `null`. Legacy string file identifiers (`"repo:<root>:<rel>"`) are accepted and stored as `null`; file attribution then comes from `payload.path` / anchor `content_hash` |
| `changedtick` | int or null | editor buffer tick when known |
| `cursor` | `{row, col}` or null | ZERO-based cursor at event time |
| `mode` | string or null | editor mode (`"n"`, `"i"`, …) |
| `payload` | object | schema per `event_type`; unknown fields are preserved, never rejected (only `edit_delta` payloads are structurally validated) |

## 5. Event types (19)

NOMENCLATURE: types are `snake_case` on the wire. Payloads are stored
verbatim (`payload_json`); the reference client sends the shapes below.

### Session lifecycle

1. **`session_start`** — `{ "machine_id": "<id>", "started_at_ms": 1758360000123 }`.
   Also an event in the batch stream (idempotent via `event_id`).
2. **`session_end`** — `{ "ended_at_ms": 1758363600123 }`. Emitted on the
   exit path; delivery is best-effort (spooled when the network fails).

### Repository context

3. **`repo_snapshot`** — `{ "root_name": "foo", "branch": "main",
   "head": "9f3a1b2c", "dirty": false, "file_count": 42 }`. Emitted after a
   successful `POST /v1/repository/snapshot`.

### Buffer lifecycle (anchors)

Anchors carry the full buffer content hash; they reset replay state.
`reason` is one of `buffer_open`, `write`, `session_start`, `rescan`,
`periodic_anchor`. Anchor emission is async (the blob uploads first): if
the buffer is reused for another file or edited while the upload is in
flight, the anchor is DROPPED, never emitted with a stale hash — a false
anchor would corrupt replay from that point. A later write / periodic /
rescan anchor re-establishes state. Deltas always chain continuously, so
replay from any surviving earlier anchor plus all subsequent deltas stays
exact.

4. **`buffer_open`** — `{ "path": "/abs/file", "content_hash": "<sha256>",
   "content_bytes": 1234, "blob_uploaded": true, "line_count": 40,
   "eol": true, "fileformat": "unix", "reason": "buffer_open" }`.
5. **`buffer_close`** — `{}` (plus envelope `file_id` when known).
6. **`buffer_enter`** — `{}`.
7. **`buffer_leave`** — `{}`.
8. **`buffer_write`** — same shape as `buffer_open` with
   `"reason": "write"` (or `"periodic_anchor"` for the every-N-deltas
   anchor). `content_hash` addresses the blob from §7.

### Text edits

9. **`edit_delta`** — the only event that mutates text. Payload is a
   line-delta (§6): `{ "path", "start_row", "old_end_row", "new_end_row",
   "deleted_text", "inserted_text", "cursor_after" }`, plus client extras
   (`changedtick`, `bytecount`) that replay ignores.

### Cursor / navigation

10. **`cursor_move`** — `{ "position": { "row": 12, "col": 4 } }`
    (both ZERO-based; `reason: "buffer_enter"` variant exists).
11. **`file_jump`** — `{ "from_file": "<file_id>", "to_file": "<file_id>" }`
    (optional `position`). Emitted when the cursor lands in a different file
    than the previous one.
12. **`mode_change`** — `{ "from": "n", "to": "i" }`.
13. **`key`** — `{ "key": "<keytrans>", "typed": true }`. Raw key identity
    only; never values of secrets (secret paths are excluded client-side).
14. **`heartbeat`** — `{ "queue_depth": 3 }`. Emitted every 60 s while active.

### Prediction lifecycle (see schemas, §10)

15. **`prediction_requested`** — model invoked.
16. **`prediction_shown`** — proposal displayed to the user.
17. **`prediction_accepted`** — proposal taken (fully).
18. **`prediction_partially_accepted`** — prefix/region of the proposal taken.
19. **`prediction_rejected`** — proposal explicitly dismissed or ignored
    until superseded.

### Future types (NOT in v1 — reserved, must be rejected as unknown today)

`undo`, `redo`, `selection_change`, `viewport_change`, `buffer_snapshot`,
`diagnostics`, `prediction_discarded`, `command_executed` are **not** v1
event types. Clients MUST NOT send them; the server rejects them with
`400`. If they are ever adopted they keep these exact names under a
protocol version bump.

## 6. Edit-delta semantics

The `edit_delta` payload replaces ZERO or more whole-line ranges:

```json
{
  "path": "/abs/src/main.ts",
  "start_row": 10,
  "old_end_row": 13,
  "new_end_row": 12,
  "deleted_text": "old line 10\nold line 11\nold line 12",
  "inserted_text": "new line 10\nnew line 11",
  "cursor_after": { "row": 11, "col": 11 }
}
```

Field definitions (all rows ZERO-based, end rows EXCLUSIVE):

| Field | Meaning |
|-------|---------|
| `path` | client-absolute path (stored opaquely; replay groups by it) |
| `start_row` | first affected row |
| `old_end_row` | exclusive end of the replaced range in the PRE-edit line array |
| `new_end_row` | exclusive end of the replacement range in the POST-edit line array |
| `deleted_text` | `"\n".join` of lines `[start_row, old_end_row)` before the edit (no trailing newline) |
| `inserted_text` | `"\n".join` of lines `[start_row, new_end_row)` after the edit (no trailing newline) |
| `cursor_after` | ZERO-based `{row, col}` cursor position immediately after the edit |

Semantics (reference client, `buffers.lua`):

- Pure insertion: `old_end_row == start_row`, `deleted_text == ""`.
- Pure deletion: `new_end_row == start_row`, `inserted_text == ""`.
- Row ranges come straight from the editor's line callback
  (ZERO-based, end-exclusive); deltas are emitted per contiguous change in
  top-to-bottom order, each with its own `sequence_number`.
- `cursor_after.col` counts characters as reported by the editor.

Replay procedure (offline or validating client):

1. Start from the nearest preceding anchor (`buffer_open` / `buffer_write`
   with `content_hash`) for the path: fetch the blob bytes, decode
   (gunzip when `compression == "gzip"`), and split into lines. Canonical
   encoding is `table.concat(lines, "\n") .. "\n"` for `fileformat=unix`
   with `eol` set (a single empty line canonicalises to `""`, so empty
   files round-trip byte-exact; a lone-newline file replays as empty).
2. For each `edit_delta` for that path in
   `(session_id, sequence_number)` order, assert the current line array
   sliced `[start_row:old_end_row]` joins to `deleted_text`; on mismatch
   the trajectory is corrupt from that point — truncate before the bad
   event and re-anchor at the next anchor event.
3. Splice: `lines[start_row:old_end_row] = inserted_text.split("\n")`
   (empty `inserted_text` splices in zero lines).
4. Re-encode canonically and compare byte-for-byte with the final file.

## 7. Blobs: sha256 content addressing + check-before-upload

- Blob identity = lowercase hex of **SHA-256 over the raw bytes**.
  Identical bytes share one blob row.
- Flow: compute hash → `POST /v1/blobs/check` (`{hashes: [...]}`) →
  upload only `missing` via `POST /v1/blobs/upload`
  (`{sha256, content_base64, ...}`).
- Anchor events (`buffer_open` / `buffer_write` with `content_hash`) and
  `repository/snapshot` manifests reference hashes. Manifest version rows
  may be ingested before the bytes arrive (logical reference); anchor
  replay requires the bytes at replay time.
- Server dedups by hash: re-upload returns `"deduped": true` (single row).
- Max single blob: bounded by the 10 MiB body cap (base64 inflates by ~4/3,
  so keep raw blobs ≲ 7 MiB). Client-side, repo files over the 1 MiB
  `max_repo_file_bytes` cap are manifest metadata only (see README scan
  behavior) and their contents are never collected.

## 8. Compression policy

- JSON request bodies are sent uncompressed (no `Content-Encoding`
  support on the server); the 10 MiB cap applies to the received body.
- Blob bytes travel base64-encoded inside JSON (`content_base64`).
- The server compresses text-like blobs with gzip **at rest**
  (`compression: "gzip"` in `blobs`, included in the upload response);
  already-compressed bytes (magic-byte sniff, compressed `mime_type`, or
  `already_compressed: true`) are stored raw.
- Servers never gzip responses.

## 9. Batching guidance

- Target **≤ 100 events (reference client default `batch_max_events`) or
  ≤ 1 MiB per batch**, whichever comes first; hard cap is the 10 MiB body.
- Flush on: batch full, **`batch_interval_ms` (default 1500 ms)**,
  session end, editor exit.
- Batches SHOULD preserve ascending `sequence_number` order (the server
  does not enforce density, but offline replay sorts by it).
- Retry failed batches with the SAME `event_id`s and `sequence_number`s —
  idempotency makes retries safe. Never renumber on retry.
- Failed batches are spooled to disk (deleted only on 2xx ACK) and retried
  oldest-first; the spool is capped at 256 MiB (oldest-first drops).
- If the client restarts with unsent events, it MUST open a NEW session and
  emit a fresh anchor per open file; resurrecting sequence numbers across
  processes is forbidden.
- Keystroke `edit_delta` events fire per editor line-callback; cursor
  positions are debounced (`cursor_debounce_ms`, default 50 ms), and a
  full anchor is emitted every `periodic_anchor_every` deltas (default 50)
  so replay stays bounded.

## 10. Prediction event schemas

Prediction payloads are stored verbatim; the reference client fills them
from the documented fields below plus `file` (absolute path) and `cursor`
(ZERO-based) defaulted from the current buffer. No reward computation
happens client-side.

| Field | Notes |
|-------|-------|
| `prediction_id` | UUID v4, links request→shown→resolution |
| `provider` | e.g. `tabcomplete-local` |
| `model` | model identifier string |
| `model_revision` | checkpoint/revision tag |
| `requested_at_ms` / `responded_at_ms` / `latency_ms` | timing |
| `context_ref` / `context_hash` | exact model input reference / sha256; lets offline tooling rebuild prompts |
| `file` / `cursor` | ZERO-based cursor + path at request time |
| `proposed_start` / `proposed_end` / `proposed_text` | range + exact proposed text |
| `max_output_tokens` / `temperature` / `confidence` / `logprob` / `finish_reason` | sampling / scoring metadata |
| `accepted_chars` / `accepted_lines` / `total_chars` | outcome counts on resolution events |

Resolution is at most one event per `prediction_id`: one of accepted /
partially_accepted / rejected. Offline tooling counts:

- `acceptance_rate = accepted / shown`
- `partial_rate = partially_accepted / shown`
- `chars_accepted_total = Σ accepted_chars` over accepted + partial events

for the model scoreboard. The collector does NOT compute these.

### 10.1 File-version sources

Every prediction payload implicitly binds to a buffer version via the
`edit_delta` chain preceding its `sequence_number` (replay ⇒ exact text)
plus `context_hash` (exact model input). When replay is unavailable, fall
back in order: nearest preceding anchor blob (`buffer_open` /
`buffer_write` `content_hash`) → `repository/snapshot` manifest hash.
Offline tooling records WHICH source anchored each example. Manifest
`source` values: `repo_scan`, `buffer_open`, `buffer_write`,
`session_anchor`, `periodic_anchor`.

## 11. Future pairing: STATE / PROPOSED / FEEDBACK / AFTERMATH

Dataset construction (offline, out of scope for this protocol) joins raw
events into training tuples:

- **STATE**: buffer text at `prediction_requested` (replay the
  `edit_delta` chain to that `sequence_number`; verify with
  `context_hash`).
- **PROPOSED**: `proposed_text` + range from `prediction_shown`.
- **FEEDBACK**: the resolution event (`accepted` / `partially_accepted` /
  `rejected` with accepted-char counts).
- **AFTERMATH**: `edit_delta` events in a fixed window (e.g. 120 s) after
  resolution on the same path — captures "accepted then immediately
  rewritten" (weak accept) vs "accepted and kept" (strong accept).

Rationale for keeping pairing OUT of the collector: pairing windows,
keep/rewrite thresholds, and label semantics are research decisions that
change per experiment. Raw events are immutable facts; any pairing is a
derived view. Storing pairs server-side would freeze today's labeling
opinion into the collection layer and make old trajectories unusable when
the opinion changes. The collector's only job is lossless capture with
enough anchors (content hashes, uncoalesced prediction-adjacent edits)
that every future pairing is computable.

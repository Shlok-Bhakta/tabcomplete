Automatic experimental suggestions are enabled, including normal-mode cursor
pauses. Quality validation remains false. Prediction never applies an edit by
itself. Automatic personalization and training remain disabled. Existing Tab
completion/snippet mappings are preserved.

The preview uses green additions and red struck deletions. Drawing the preview
does not change source text. Acceptance rechecks buffer/file identity, version,
source/range hashes, cursor compatibility, UTF-8 boundaries and active proposal
identity, then applies an atomic edit with a separate undo boundary. Syntax
filtering is deliberately disabled for this experimental installation, as the
user requested. Wire, termination, range and staleness checks remain enforced.

Restart an already-open Neovim process to load an updated plugin. A machine
reboot is not required for TabComplete. After the user's NixOS switch, SSH
confirmed `tabcomplete-engine.service` active and the expected model health
response on port 19094.

## What this model actually predicts

The current task is **cursor-local fill-in-the-middle**, with trained PSM marker
order. It sees source before the cursor and source after the current physical
line, and predicts the remainder of that logical source line. The plugin wraps
the result as an edit preview. The model must terminate with its real EOS within
the 96-token output ceiling; a cutoff is not a valid completed action.

This is not evidence of general next-edit prediction. It does not freely choose
an earlier edit location or have a trained, dedicated representation of recent
editor actions and other open files. Existing edits visible in the source can
provide clues, but the user's example of repeated renaming across lines needs
a separate trajectory/history-aware task and evaluation. Adding arbitrary
history or repository text to the trained prompt is not an established fix.

## Scientific history and what it supports

1. **Small foundation comparison.** Q25, Qwen3 Base, LFM350 Base and the existing
   P12 control were screened. Q25 and Q3 learned a small generated next-edit
   grammar perfectly. Its close template relatives and limited families did
   not establish real-editor intent quality. Q25 was selected on measured
   deployment tradeoffs. The original Q4 hash `a45bc50a…` belongs to that older
   model, not the model now served.
2. **Experimental automatic feedback.** Automatic suggestion display was
   separated from quality validation. A bounded debounce/state machine,
   cancellation, incremental SSE, explicit acceptance, persistence, feedback
   taxonomy and same-database projections were installed. Automatic training
   stayed off.
3. **Sweep evaluation.** Sweep 1.5B Q8 and Q4 were tested. Historical raw code
   controls scored 10/200 versus 6/200 functional success and 30/180 versus
   28/180 exact line completion. Publisher-prompt full-file behavior had
   protocol/range/multiline problems; changed full-file CPU requests took
   seconds. Q8 exceeded the 1.5 GiB service limit. These measurements did not
   justify using Sweep for the one-line prototype. Missing GPU next-edit Q4
   results were recorded as missing, not filled in.
4. **Rust engine and preview.** Local context/inference/delivery moved into the
   Rust engine. Embedded single-model binaries and declarative Nix delivery
   were implemented. Raw-payload hashes showed the earlier escaped quotes came
   from model output, not accidental double JSON decoding. We did not blindly
   remove legitimate backslashes. Diff previews, normal-mode requests,
   Alt+p, explicit syntax-filter opt-out and navigation feedback semantics
   followed.
5. **Code pretraining versus direct completion.** A bounded raw-code pass used
   7,872,512 input tokens. Functional strict-code success stayed 10/200. Both
   completion arms then received the same 4,096 public-source FIM states,
   one pass each, 1,776,908 input and 34,405 supervised target/EOS tokens.
   Untouched Q25 → FIM improved from 47/240 to 130/240 exact EOS completions;
   code-pretrained Q25 → FIM ended at 127/240. The paired difference was
   inconclusive. Extra raw code did not establish a final completion gain.
6. **Selected native export.** The direct FIM model scored 126/240 exact,
   valid, EOS-terminated actions in native Q4 versus 130/240 in HF FP16.
   That changes runtime and precision together, not only quantization.
   General raw causal success was still only 11/200; raw line exact was
   16/180 and dedicated FIM line exact 85/180. These are different tasks.
7. **ThinkPad update.** The previously selected direct FIM checkpoint was
   installed declaratively, real inference/editor/database smoke verified,
   and actual laptop timings collected. The user's successful Rust suggestion
   is from this completed model, not today's new training run.
8. **Current scaling study.** Two untouched-Q25 arms were frozen before
   outputs: repeat 4,096 states twice versus 8,192 states once, both 8,192
   exposures and 512 updates. The latest user instruction permits finishing
   only the active repeat arm before pausing. Without the scaled arm, this
   study cannot answer the matched repetition-versus-new-data question.

## Laptop latency and the cache bottleneck

Eight requests per provider, two repetitions of four fixed synthetic states,
ran with existing user applications present. These are a small normal-workload
slice, not a proven controlled measurement. Old and new providers differ in
weights, task protocol and context, so they are not a pure runtime ablation.

| Observation | Previous next-edit Qwen | Current FIM Qwen |
| --- | ---: | ---: |
| Actual prompt tokens | 392–393 | 643 |
| Changed-state completed HTTP median | 700.6 ms | 3,719.9 ms |
| Identical-prompt repeat | 434.9 ms | 79.6 ms |
| Peak model-service RSS | 581,107,712 B | 592,429,056 B |

For current FIM, compatible changed states reused 640 tokens and completed in
about 94–95 ms. Sliding the left edge of the last-640-token window reused only
one token, then spent approximately 3.65–3.77 seconds in prefill. Decode took
about 21–52 ms. Identical repeats reused 642 tokens. The user may encounter
fast favorable cached states and slow incompatible ones; repeat latency is
not a general editing-latency promise.

Selected peak PSS was 588,277,760 bytes. Swap activity, process swap and memory
pressure increases were zero in this selected window. Helper/editor memory was
not separately measured. Do not infer thrashing from unrelated swap occupancy.

Four versus two generation threads were also tested earlier on crabcake; four
were retained. That desktop evidence is not a ThinkPad thread ablation.
TurboQuant has no compatible implementation in the pinned CPU runtime. Q4
weights and standard F16/Q8 KV storage are not TurboQuant.

An isolated branch, `prototype/q25-fim-context-window-r1`, implements an
explicitly versioned, opt-in aligned prefix window. It can stabilize cache
prefixes by discarding additional context, so it needs paired quality testing.
Its isolated branch was pushed at
`c9b7393b39f9c6ff1a063efcd7e019dcb9111161`. Rust passed 49 tests and Lua
passed 94. It is not deployed or inference-benchmarked; those focused tests
do not establish model quality or latency. No aligned-policy latency gain is claimed. Ordinary
client cancellation already preserves completed input state; a cancellation
retention rewrite is unnecessary. One active sequence cannot preserve both
file A and B across A→B→A without a separate bounded snapshot policy.

## Decisions to revisit after the pause

- Decide whether to finish the unallocated scaled arm. Repeat-only results
  cannot distinguish extra repetition from extra distinct data.
- Evaluate the opt-in aligned context window with fixed public cases and real
  changing-state timing before any declarative deployment.
- Define actual editor next-edit prediction separately from source FIM.
  Recent-edit histories, repeated-renaming trajectories, defensible no-edit
  examples and multi-file context need suitable supervision and held-out tests.
- Public edit data has reconstruction, actor attribution, licensing and split
  constraints. Keep commit diffs and generated trajectories clearly separate
  from witnessed human editor histories. A data-source audit is being preserved
  with the handoff; it is not a completed next-edit training set.
- Keep the useful installed checkpoint and rollback artifact stable while
  experimenting. No automatic live personalization or guaranteed monotonic
  improvement.

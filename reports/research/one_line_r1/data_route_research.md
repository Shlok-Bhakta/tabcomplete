The code-review corpus is the only new source with enough *raw* rows and all four languages. It is not yet a licensed, inferability-checked next-edit set. A bounded next audit could stream at most 100 **train-only** rows, capped at 25 per language and spread across repositories, after resolving the dataset terms. For each row, pin the dataset revision and PR source, verify the source file license, reconstruct a single-line action, exclude the reviewer comment and PR title from student input unless they were demonstrably available in the target UI, and have an independent reviewer judge whether the target follows from visible state. Retain the repository split and log every rejection. If the four-language counts or acceptance yield are weak, stop before a larger sample. This is a proposed audit, not permission to treat review outcomes or negatives as next-edit labels.

Our [local inventory](source_inventory.json) records two 100-case Git pilots from four repositories. The second pilot has 100 structurally replayable cases with nonempty history. Ninety-five edit rows use reconstructed order inside a commit; five keep rows are synthetic terminal controls. None passed an independent inferability review. Accepted train, development, and test counts remain 0, 0, and 0. The 100 pinned public authoring seeds cover 25 Python, 25 TypeScript, 25 Rust, and 25 Go repositories, with a verified MIT repository license at each pinned commit. They have no accepted labels. Only one source file has an explicit SPDX notice, so per-file provenance needs continued review.

The existing collector at `/mnt/ssd/collector-data/collector.sqlite` contains 573 `edit_delta` events and 70 prediction projection rows at this observation time. A read-only query found zero prediction events marked `human_verified=true` and `synthetic=false`. Some older events omit both fields; they cannot be promoted to verified human decisions. The collector therefore offers a useful future data path, but no verified preference labels today.

A deterministic first-eight inspection of the existing 100-row Git-history pilot illustrates the inferability problem; it is not a random quality estimate. In `pallets/itsdangerous`, consecutive extracted targets include adding a `# pyright: ignore` comment, changing `hashlib.sha1` to `_lazy_sha1`, and several generic type substitutions. Their prior single-line edit often occurred dozens of rows away. Exact commit chronology and byte replay identify what happened in Git, but the visible editor state alone does not establish why those particular changes should be the next edits. These remain unreviewed candidates, not labels.

## Bounded 100 to 1,000 cross-commit pilot

Use the 100 pinned, licensed repository seeds as the first sampling frame. For each repository, inspect a bounded same-file first-parent commit chain and retain exact commit and blob hashes. Select a prior edit from one commit and a target one-line edit from a later commit. Keep actual commit chronology and label it as such. Never invent edit order within a commit. Do not put target commit messages, target diffs, focus hints, or answers into the student input. Fetch only the needed commit metadata and old/new file blobs, with a 100 MiB aggregate transfer stop and per-repository cap. Record failed or unavailable repositories rather than replacing them after seeing task quality.

Freeze candidate selection and splits before review. Exclude any repository related to a reserved evaluation group. Verify the repository license at the pinned revision, inspect file notices and copied-content risk, reconstruct the exact pre-state, apply the prior edit and target action byte-for-byte, check tokenizer and 64-token response limits, and deduplicate source and target states across groups. A blind reviewer then sees only the student-visible state and judges whether the prior edit and context make the target useful and inferable. An independent reviewer checks the proposed objective or executable property. A structurally valid patch alone does not pass. Do not manufacture keep labels from untouched lines or idle time.

Start with up to 100 candidates, aiming for one from each of the 100 repositories and 25 per language. Predeclare an expansion gate of at least 60 accepted cases overall, at least 10 accepted cases per language, and no unresolved license or split violations. If that gate passes, freeze a new 1,000-candidate frame from distinct verified repositories in the existing R2 discovery pool and repeat the same review, without reusing the first 100 as independent evidence. Log every sampled, rejected, and missing case so yield has a denominator. If the first gate fails, revise the data source or task evidence under a new plan before sampling more Git history.

The 60% gate is a planning threshold, not an observed yield. Even at that rate, 20,000 accepted states would require roughly 33,334 screened candidates, plus distinct development and test groups. The available R2 pool has many repository aliases, but availability, per-file licensing, inferability, and reviewer capacity are unverified. This route does not yet meet the 20,000-state floor, the 25 reviewed mechanism requirement, or a defensible no-edit class.

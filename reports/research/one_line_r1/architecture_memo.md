# Mamba-3 SISO 443M feasibility preflight

The official [`state-spaces/mamba3-siso-443m`](https://huggingface.co/state-spaces/mamba3-siso-443m/tree/efe60ce987877fcb72f089ab3a94478e99e2a6ae) checkpoint is Apache-2.0, 443M parameters, 24 layers, and 2,048-token pretrained context. The card points to the separately gated [`meta-llama/Llama-3.1-8B`](https://huggingface.co/meta-llama/Llama-3.1-8B) tokenizer without pinning its revision. No Mamba weights were downloaded.

The [official SISO source](https://github.com/state-spaces/mamba/blob/e9594ce1c732d97440f0332fdc43170a2294dbfa/mamba_ssm/ops/triton/mamba3/mamba3_siso_combined.py#L393-L399) casts intermediate tensors to BF16, and its [forward kernel](https://github.com/state-spaces/mamba/blob/e9594ce1c732d97440f0332fdc43170a2294dbfa/mamba_ssm/ops/triton/mamba3/mamba3_siso_fwd.py#L222-L268) uses TMA descriptors. A T4 is compute capability 7.5; NVIDIA documents BF16 support on 8.0+ and TMA on Hopper 9.0. Casting model weights to FP16 would not remove either kernel requirement. Consequently, a correct matched T4 SFT run is not supported by this official path.

The installed llama.cpp revision `f072b103714dfa1eee531f80b24512faf38e3dd2` has no Mamba-3 converter/runtime implementation, so a target-CPU Q4 path is not established. The [paper](https://arxiv.org/abs/2603.15569) and model card do not provide code or next-edit results for this exact checkpoint. A fair future comparison would need the same frozen groups, examples, action codec, loss normalization, budgets, and measured serving behavior on the intended machine. This static preflight neither loads the checkpoint nor proves it cannot work in a future supported stack; it does not block q25.
